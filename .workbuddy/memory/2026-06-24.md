## FFmpeg/FFprobe 使用与压缩参数优化分析

对项目核心功能（FFmpeg/FFprobe 调用与压缩参数）做了全链路代码审查，产出分析报告 `ffmpeg-optimization-analysis.md`。

### 关键发现

**P0（稳定性，建议立即修）**
- `ffprobe_media_analyzer.dart` 用 `.timeout()` 但不 kill 进程，超时后 ffprobe 子进程变僵尸，批量分析时累积泄漏。
- `local_ffmpeg_process_observer.dart` 缺少 stall detection，ffmpeg 进程挂死（网络盘 IO、硬件编码器死锁）时任务永久卡 running，阻塞队列。

**P1（效率/一致性）**
- `ffmpeg_command_step_builder.dart` 的 two-pass 在 `targetVideoBitrate == null`（CRF 模式）下仍跑两遍，无意义浪费一倍时间。
- 码率上限表在 `default_compression_advisor.dart` 和 `compression_estimator.dart` 重复维护，易不一致。
- `out_time_ms` 字段歧义（实为微秒），建议优先用 `out_time_us`。
- 预览帧生成串行执行 3N 次 ffmpeg。

**P2（体验/性能）**
- preset 固定 slow 无速度出口；硬件编码走 CPU lanczos scale；Windows 内存检测缺失；缺 `-stats_period`；VFR 进度倒退未单调化。

### 架构优点（保持）
编码器能力探测+降级、HDR/Alpha/色彩元数据处理、资源调度（CPU+内存+线程预算）、压缩无效输出检测+格式 fallback、任务队列插队/抢占设计均较成熟。

## P0 修复实施

### P0-1: ffprobe 超时僵尸进程
- 文件：`lib/infrastructure/services/input_runtime/ffprobe_media_analyzer.dart`
- 改 `Process.run(...).timeout()` 为 `Process.start` + 手动收集 stdout/stderr buffer + `exitCode.timeout(timeout)`。
- `on TimeoutException` 分支主动 `process.kill(sigkill)` 并 `await` exitCode + 流关闭（带 2s 兜底超时），避免句柄残留。
- 接口签名与抛出 `TimeoutException` 的行为保持不变；新增 `dart:async` 显式 import。

### P0-2: FFmpeg observer stall 检测
- 文件：`lib/infrastructure/services/execution/local_ffmpeg_process_observer.dart`

- `observe` 内启动 `Timer.periodic`，跟踪 `lastActivity`（stdout/stderr 有数据即刷新），超阈值 `kill(sigkill)` 并标记 `stalled`，exitCode 完成后返回 failed（消息含"无响应超时"）。

## 暂停→睡眠→恢复 场景：当前处理行为梳理

用户问"现在项目是什么样子、会怎么处理这个场景"，梳理了当前代码的完整处理路径（已落到上方时序图的可视化中）：

### 当前实际行为链路
1. **用户点击暂停** → `_pauseExecution` → `SignalFfmpegProcessController.pause()` → `process.kill(SIGSTOP)` → ffmpeg 进程冻结，状态切 paused。
2. **笔记本息屏 / 系统睡眠** → 所有进程冻结；VideoToolbox 硬件编码会话可能被系统回收（GPU 上下文丢失）。ffmpeg 进程仍在，但内部 VT session 已 invalid。
3. **唤醒后用户点击继续** → `resumeExecution` → `SignalFfmpegProcessController.resume()` → `process.kill(SIGCONT)` → ffmpeg 进程解冻尝试恢复编码。
4. **若 VT 会话已失效** → ffmpeg 立即报错退出（exitCode 187，stderr: Generic error in an external library）。
5. **observer 上报** → `LocalFfmpegProcessObserver` 捕获 exitCode≠0 + stderr tail → `FfmpegProcessObservation.failed` → `finishObservedTask` 被调用。
6. **auto-retry 兜底（上一轮已加）** → `_isHardwareEncoderSessionFailure` 判定（含 videotoolbox + Generic error）命中 → `hardwareRetryCount(0) < maxHardwareEncoderRetries(1)` → `deleteStepOutput` 清理残缺输出 → `startExecutionStep` 从头重启该 step，全新 VT 会话。
7. **任务继续编码到完成**，用户感知：进度回退了一下后自动恢复。

### 当前方案的局限
- 软件编码器（libx264/libx265）：SIGSTOP/SIGCONT 无缝挂起，不受睡眠影响。
- 硬件编码器：恢复时 VT 会话已失效必然失败 → auto-retry 救回来但**当前 step 进度归零**（用户感知到进度回退）。
- 没有断点续编，与 HandBrake 一致（已做竞品调研确认）。
- 已客观分析 concat 断点续编方案 ROI 不划算（630 行 + 永久维护税），建议保持现状（auto-retry 兜底）或上"方案B：硬件编码暂停=终止+重启step"（约 40 行，避免 SIGCONT 后必经一次失败才救回的延迟）。

### 关键代码位置
- `lib/infrastructure/services/execution/signal_ffmpeg_process_controller.dart`：pause=SIGSTOP, resume=SIGCONT, terminate=SIGTERM
- `lib/application/services/execution/ffmpeg_task_queue_runner.dart:1068`：`resumeExecution`
- `lib/application/services/execution/ffmpeg_task_queue_runner.dart:1234-1244`：auto-retry 入口
- `lib/application/services/execution/ffmpeg_task_queue_runner.dart:1321-1394`：`_isHardwareEncoderSessionFailure` + `_retryHardwareEncoderStep`

## 失败通知友好化

用户反馈"通知里报一大堆错误"，优化通知/通知中心的失败消息为用户友好文案。

### 改动
- `lib/application/services/execution/ffmpeg_task_queue_runner.dart`：
  - `failureSummary` 不再把 `task.errorMessage` 原封塞进 `failureReason`，改为调用新增的 `_friendlyFailureInfo(rawError, mediaKind)` 做翻译。
  - 新增 `_friendlyFailureInfo`：覆盖 10+ 种常见错误模式（硬件会话失效/源文件不可访问/权限/磁盘空间/编码器不可用/源文件损坏/stall超时/无效压缩/输出缺失/兜底），返回 `({reason, suggestion})`。未识别错误走兜底文案，不再暴露 stderr 技术细节。
  - `failureSuggestionFor` 改为复用 `_friendlyFailureInfo`。
- `lib/application/services/app_notifications/app_notification_manager.dart`：
  - `_failureReason`：优先用 summary 的友好化 reason；summary 缺失时不回退到 task.errorMessage，走兜底友好文案。
  - `_failureSuggestion`：保留无 summary 时的场景判断兜底（图片/音频无效压缩），其他走兜底建议。
- `task.errorMessage` 保持原始技术信息不变，供任务日志对话框等"主动查看详情"场景使用。
- 测试 `test/app_notification_manager_test.dart`：新增 VT 会话失效友好化测试 + summary 缺失兜底测试。

### 覆盖的错误模式 → 友好文案
| 模式 | 友好原因 | 友好建议 |
|------|---------|---------|
| VT/NVENC/QSV/AMF + Generic error | 系统挂起或睡眠导致硬件编码会话中断 | 任务已自动尝试恢复。如仍失败，建议改用软件编码后重试 |
| No such file / 源文件不存在 | 源文件不可访问，可能已被移动或移除 | 确认源文件仍在原位置，U 盘/移动硬盘已连接 |
| Permission denied | 没有输出位置的写入权限 | 检查输出目录权限，或选择其他保存位置 |
| No space left / disk full | 磁盘空间不足，无法写入输出文件 | 清理磁盘空间后重试 |
| Unknown encoder / not supported | 当前 FFmpeg 版本不支持所需的编码器 | 检查 FFmpeg 版本，或改用其他编码器 |
| Invalid data / moov atom not found | 源文件可能已损坏或格式不受支持 | 确认源文件能否正常播放 |
| 无响应超时 | 处理进程长时间无响应，已自动终止 | 可能由网络盘 IO 或硬件编码器死锁引起 |
| 兜底 | 媒体处理未能完成 | 查看任务日志获取详细信息，或重试 |
