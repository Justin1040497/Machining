## 应用更新系统全面审查

对 FrameLean 的应用更新系统做了逐行代码审查，产出审查报告，状态「审查中，待讨论」。

### 产出
- `docs/decisions/260623-update-system-review.md`

### 审查覆盖
- 客户端：app_update_provider / application services / infrastructure / domain value objects / UI dialogs
- 服务端：UpdateService.kt
- 测试 + 决策文档 260616 / 260620

### 发现的关键缺口（P0）
1. mandatory / minSupportedBuild 字段解析了但从未在 UI/业务逻辑中强制执行——强制更新形同虚设
2. 下载 URL（COS 预签名）未强制 HTTPS——updateBaseUrl 校验了但实际下载 URL 没校验
3. 跨重启恢复路径（_tryRestorePersistedDownload）只做 SHA-256，跳过 Ed25519 签名校验——与下载路径不一致
4. 下载无超时——await for (chunk in response) 在连接挂起时无限阻塞

### 其他重要缺口
- 无自动重试 / 无周期性检查 / 无磁盘空间预检
- 无回滚机制（sentinel 文件单点故障）
- macOS DMG 路线可能完全无签名校验
- exit(0) 过 abrupt（不给 dispose 机会）
- 状态文件非原子写入
- 无下载速度/ETA、错误消息技术化、无 snooze

### 优点
分层架构清晰、双校验机制、断点续传逻辑严谨、企业托管配置多来源、三入口 UX

## 更新提示交互重构方案（ADR 产出）

用户反馈当前更新提示信息密度过高、日志页面冗余。讨论后确认需求：保留设置页检查更新按钮，工作台右上角轻提示尾部加 `›` 打开通知弹窗，弹窗底部三按钮（立即更新/下次再说/查看完整日志），日志页唯一入口为弹窗。

### 产出
- `docs/decisions/260623-update-ux-redesign.md` — 状态「提议，待确认」

### 方案核心
- 三层信息密度：L1 右上角胶囊轻提示 → L2 通知弹窗(380×320) → L3 版本日志页
- 入口收敛：删除设置页「版本日志」按钮，日志页唯一入口为弹窗「查看完整日志」
- snooze 机制：「下次再说」= 记录 version，同版本开机不再自动弹，新版本恢复
- 开机自启：有更新+未 snooze → 延迟 2 秒弹 L2
- 设置页检查更新保留：有更新→弹 L2，无更新→轻提示
- mandatory 更新：隐藏「下次再说」，弹窗不可关闭（待确认）

### 待确认
1. mandatory 弹窗是否阻断不可关闭
2. L2 弹窗是否阻断（用户能否操作工作台）
3. 通知中心历史版本点击：弹 L2 还是直接进 L3
