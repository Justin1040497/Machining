# 项目执行工作流

## 文档目的

这份文档记录 FrameLean 从需求讨论到 PR 准备的完整项目执行流程。它约束 AI agent 和开发者如何讨论方案、创建分支、设计测试、实现、验证、更新文档和准备提交信息。

Git 分支、提交、worktree、PR 和发布细节仍以 `docs/develop/git-workflow.md` 为准；本文件负责更上层的项目执行顺序。

## 核心原则

- 先理解项目，再讨论方案；不能只读文档，也不能只看用户描述。
- 如果文档和当前代码不一致，并且代码已经明显推进到文档之后，以当前代码为准，同时在文档阶段修正文档。
- 如果代码偏离了仍有效的架构或流程规则，需要指出风险，而不是默认代码正确。
- 不能直接附和需求，需要给出更成熟的企业级、市场产品级或长期维护更稳的方案。
- 需求、测试设计和实现后都需要边界确认；用户明确说“可以”后再进入下一阶段。
- `main` 只能作为长期主干，日常改动必须通过短分支和 PR / MR 合入。

## 阶段 1：需求理解与方案讨论

适用于新功能、bug 修复、架构整理、产品方向讨论、工程治理和发布相关工作。

开始前必须：

1. 阅读 `AGENTS.md`。
2. 阅读 `docs/README.md` 和相关 `docs/` 文档。
3. 搜索并阅读相关源码、测试、脚本和配置。
4. 对比文档和项目实况，判断文档是否滞后。
5. 如果方案依赖框架、API、工具链、行业实践或成熟产品做法，查阅官方文档和可信专业资料。

讨论时必须：

- 不无条件认同用户提出的方案。
- 明确指出方案的长处、短板、风险、成本、测试难度和长期维护影响。
- 可以提出更合适的企业级或产品级方案。
- 持续追问业务边界、异常情况、兼容范围和验收标准。
- 在用户明确说“可以”前，不进入执行。

## 阶段 2：分支或 worktree 准备

进入执行前必须确认当前 Git 状态。

规则：

- 不能在 `main` 上直接开发或提交日常改动。
- 按需求类型选择 `feature/*`、`fix/*`、`chore/*`、`docs/*`、`release/*` 或 `hotfix/*`。
- 分支名使用小写英文、数字和短横线。
- 创建分支前给出 2 到 4 个合适候选，让用户选择或确认。
- 当前工作区有其他开发中的改动时，优先在 `worktrees/<task-slug>` 创建独立 worktree。
- 新分支应基于最新远程 `main`；创建或打开分支后检查远程是否有新提交。

详细规则见 `docs/develop/git-workflow.md`。

## 阶段 3：测试用例设计

写代码前先设计测试。

按需求类型选择验证方式：

- bug 修复：先设计复现测试或回归测试。
- 新功能：优先覆盖领域模型、application use case 和关键 UI / widget 行为。
- 架构整理：先保护现有行为，再移动边界。
- 产品方向：先定义用户场景、验收标准或原型验证方式。
- 脚本和发布流程：验证命令、产物路径和关键文件布局。

测试设计需要说明：

- 要保护的行为。
- 计划新增或修改的测试文件。
- 关键边界和异常情况。
- 不纳入本次范围的内容。
- 必要的手动验证。

用户明确说“可以”后，才开始写测试。

## 阶段 4：实现

实现必须严格服从已确认的需求和测试边界。

规则：

- 不顺手增加未确认功能。
- 不做无关重构或大范围格式化。
- 遵循当前项目架构：`features -> application -> domain`，`infrastructure` 实现 application 抽象并依赖 domain。
- 如果文档落后于当前实现，以项目实况为准，并在文档阶段补齐。
- 优先复用项目已有 helper、provider、use case 和组件模式。
- 单文件不应无必要膨胀到 800 行以上；除非是生成文件、框架入口或强内聚库文件。

实现完成后需要总结：

- 完成了什么。
- 哪些测试或业务边界被满足。
- 什么没有做。
- 是否存在模糊边界或需要用户检查的业务判断。

用户明确说“可以”后，才进入验证和审查。

## 阶段 5：审查与验证

验证需要覆盖代码、业务边界和项目工具链。

Dart / Flutter 改动默认执行：

```bash
git ls-files '*.dart' | xargs dart format --set-exit-if-changed
flutter analyze
flutter test
```

根据改动范围追加：

- 构建脚本变更：执行对应脚本或做语法 / 产物结构验证。
- 打包变更：验证 macOS 或 Windows 产物中的关键运行时文件。
- CI 变更：验证 YAML 和 workflow 关键路径。
- UI 变更：进行手动检查或截图验证。
- 架构变更：检查依赖方向、测试覆盖和文档是否同步。

如果发现问题，需要说明问题、原因、修复方式和复验结果。

## 阶段 6：文档、同步与 PR 准备

当改动影响架构、数据模型、测试、发布流程、用户可见行为或开发者工作流时，必须更新文档。

常见文档位置：

- `docs/develop/architecture.md`
- `docs/develop/data-model.md`
- `docs/develop/test-plan.md`
- `docs/develop/technology-stack.md`
- `docs/develop/git-workflow.md`
- `docs/product/roadmap.md`
- `docs/reference/`
- `docs/archive/changelog.md`

每次提交准备前都要更新 `docs/archive/changelog.md`。bug 修复还需要在 `docs/archive/logs/` 添加聚焦问题日志。

文档更新后：

1. 拉取或同步最新远程代码。
2. 检查是否有冲突。
3. 重新执行阶段 5 中与本次改动相关的验证。

除非用户明确要求，agent 不能直接执行 `git add`、`git commit` 或 `git push`。

结束时需要给出：

- 本次改动概要。
- 已执行检查及结果。
- commit message 候选，格式为 `<type>(scope): 中文摘要`。
- 如果需要 PR，给出 PR 标题和 description 草稿。
