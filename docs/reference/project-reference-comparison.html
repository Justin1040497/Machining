Machining 与参考项目差异对比报告

范围与结论

`.reference` 不是一个单一项目，而是两个参照物：CompressGo 更像同阶段产品参照，HandBrake 是成熟工业级转码器参照。

总判断：Machining 的非 UI 代码最强的是分层清晰、领域模型明确、FFmpeg 命令与进程观测可测试；CompressGo 的优势是功能覆盖更宽、Tauri sidecar/事件协议更完整、硬件检测更贴近真实运行；HandBrake 的优势是把媒体处理沉淀成稳定内核、预设协议、状态协议、构建协议和许可证协议。
Machining

更像“干净的产品内核”

Dart 领域对象、仓储接口、服务接口、Drift 持久化、FFmpeg command plan 与队列执行器分开。适合继续演化，但功能和发布协议还偏 1.0。

CompressGo

更像“快速集成型工具”

Vue/Pinia 负责任务与设置，Rust Tauri command 直接操控 FFmpeg、事件和进程。功能广、反馈快，但边界比 Machining 松。

HandBrake

更像“媒体处理平台”

核心是 libhb，不依赖外部 FFmpeg CLI 协议；它有公共 C API、JSON job/preset、完整状态机、contrib 构建和跨平台发布体系。

项目形态差异

统计只用于把规模放到同一坐标系，不代表质量高低。

架构与数据流

这里对比的是业务和系统边界，不评价界面呈现。

Machining 当前做得好
  • 采用近似 Clean Architecture 的分层：domain 保存实体/枚举/值对象，application 定义仓储和服务协议，infrastructure 放 Drift、FFmpeg、文件系统实现。
  • FFmpeg 执行被拆成“构造命令”“启动进程”“观测进度”“队列调度”四段，单元测试可以替换每段依赖。
  • 任务状态持久化到 SQLite，任务恢复、源文件指纹、分析结果失效等流程比 CompressGo 更接近生产应用。
  • 命令构造支持单遍和目标体积两遍计划，FfmpegCommandPlan.steps 是一个很好的扩展点。
CompressGo 的不同路线
  • 它的任务与设置主要是前端内存状态：useTaskStore、useTaskSettingsStore、useBatchProcessor、useTaskStateController。
  • Rust 后端不是严格分层服务，而是 Tauri command 直接完成路径解析、FFprobe、命令拼接、进程管理、事件发送。
  • 这种路线功能推进快，适合桌面工具早期验证；代价是 Rust 侧重复路径解析多、业务策略与系统调用耦合较重。
HandBrake 的架构参照

HandBrake 的核心经验不是“多写代码”，而是把媒体处理抽象成稳定内核。libhb 对外暴露 hb_scan、hb_add、hb_start、hb_pause、hb_resume、hb_get_state 等 API；UI、CLI、平台前端围绕同一个 job/state/preset 协议工作。Machining 目前通过 FFmpeg CLI 组合命令，短期更轻；长期如果功能扩展到音轨、字幕、滤镜、批量预设，就需要像 HandBrake 一样把“任务协议”做成稳定的数据结构，而不是把更多参数塞进页面状态。

Machining
导入文件 → 生成 MediaTask → 读取源文件指纹 → FFprobe 分析 → 保存分析结果 → 命令计划 → 队列运行 → 进度观测 → 写回 SQLite。
CompressGo
前端创建 CompressionTask → 选定 settings → invoke('compress_video') → Rust 启动 FFmpeg → 用 Tauri event 把命令/进度/完成/错误推回前端。
HandBrake
扫描 source/title → 预设清洗/导入 → 生成 job dict → libhb 执行工作线程 → UI/CLI 定期读取 hb_state_t 或 JSON state。

编码策略

“编码策略”包含代码组织、类型建模、错误处理、测试和媒体编码参数策略。

策略维度 Machining CompressGo HandBrake
类型建模 强类型枚举和值对象：VideoCodec、EncoderBackend、CompressionMode、MediaAnalysisResult。优点是测试稳定；风险是枚举用 name 入库，重命名会破坏旧数据。 TypeScript 接口 + Rust serde 结构体，前后端通过字段名契约对齐。快，但缺少集中 schema/version 机制。 C struct + JSON dict + preset version。字段多但协议稳定，并显式提醒跨语言绑定同步。
命令/参数构造 集中在 DefaultFfmpegCommandBuilder，支持输出路径去重、HEVC hvc1 tag、+faststart、两遍压缩、硬件参数分支。 Rust command 内联拼接；支持更多编码器、bit depth、time range、音频 copy/WebM Opus、图片格式。 不直接拼 FFmpeg CLI，而是使用 libav/libx264/x265 等库能力与内部 job 结构，参数被编码为 preset/job 协议。
硬件编码 解析 ffmpeg -encoders 中的 encoder 名称，再按平台优先级选择。轻量、可测，但可能把“列出支持”误判成“实际可用”。 会用测试视频做最小 1 帧编码检测，并缓存 hardware_support.json。这比只解析列表更接近真实运行。 编译期特性、运行期能力、平台 API 都纳入内核，支持 QSV/NVENC/AMF/VideoToolbox 等更细粒度矩阵。
队列与进程 队列执行器维护前台任务和暂停执行上下文，状态写回仓储。macOS 的 SIGSTOP/SIGCONT 路线清晰；Windows 暂停恢复需要补强。 Rust 全局 HashMap 管理子进程，Unix 用 kill STOP/CONT，Windows 用 ToolHelp 枚举线程 suspend/resume。 libhb 内部线程、锁和状态结构管理，不依赖 OS 暂停外部进程；暂停时间会纳入 ETA 计算。
测试策略 目前最扎实。命令参数、极限压缩确认、队列切换、多步骤 plan、进度解析、输出缺失等都有单测。 更多是运行时日志和事件调试，自动化测试薄弱。适合借功能，不适合照搬工程质量。 成熟项目的 CI、CLI 测试、构建矩阵和贡献流程完整，但成本也最高。

协议遵守方式

这里的“协议”按五类理解：FFmpeg/FFprobe、进程生命周期、数据/job、平台权限、许可证/分发。

Machining

遵守方式

  • FFprobe 协议：使用 -v error -print_format json -show_format -show_streams，解析视频/音频流、容器码率、估算码率。
  • FFmpeg 进度协议：主任务使用 -progress pipe:1，观测 stdout 中的 out_time_ms 并按分析时长计算进度。
  • 输出封装协议：MP4/MOV 自动加 -movflags +faststart，HEVC in MP4/MOV 加 -tag:v hvc1。
  • 本地持久化协议：Drift schema 版本迁移、任务状态落库、分析结果和源文件指纹落库。
  • 分发协议：有 FFmpeg/x264 GPL 路线文档、构建脚本和二进制不提交策略。
CompressGo

遵守方式

  • Tauri 权限协议：capabilities/default.json 显式允许 sidecar bin/ffmpeg 与 bin/ffprobe 执行。
  • 事件协议：按 taskId 生成 compression-progress-*、compression-completed-*、compression-error-* 等事件名。
  • 硬件检测协议：除解析 -encoders 外，还执行最小编码测试并缓存结果。
  • 平台协议：Windows 通过 Win32 ToolHelp 暂停/恢复进程线程，避免简单套用 Unix 信号。
HandBrake

更成熟的协议化

HandBrake 的协议遵守方式是“内核化”：扫描、预设、job、state、进度、错误、构建依赖和许可证都被定义成可复用协议。hb_state_t 明确区分 IDLE、SCANNING、WORKING、PAUSED、WORKDONE、MUXING；hb_state_to_dict 把状态转换为 JSON；preset API 会导入、清洗、升级旧字段。它遵守的不是某个单点 CLI 参数，而是一整套跨前端、CLI、平台和发布流程的协议。

对 Machining 的关键启发：目前最该补的不是重写为 HandBrake 式内核，而是把现有 FFmpeg 外部进程协议再收紧：实际硬件编码探测、跨平台暂停、结构化日志/事件、发布包许可证材料、schema 文档同步。

当前缺口

下面是非 UI 维度里最值得尽快处理的差距。

协议风险
  • Windows 暂停恢复：当前队列执行器直接使用 ProcessSignal.sigstop/sigcont，这更像 Unix/macOS 路线；CompressGo 已对 Windows 单独实现线程暂停恢复。
  • FFmpeg stdin/覆盖策略：主压缩命令依靠输出路径去重避免覆盖，但没有统一加 -nostdin 或 -y。若路径竞态或 FFmpeg 触发交互，存在挂起风险。
  • 硬件能力误判：只解析 encoder 名称，不代表当前 GPU、驱动、像素格式、输入样本真的可编码。
  • macOS 打包行为不一致：README 说内置运行时是目标；Windows 缺二进制会 fatal，macOS build phase 缺二进制只是 warning 并跳过复制。
工程风险
  • 文档漂移：docs/architecture/data-model-v1.0.md 写 schema 版本 7，而代码 AppDatabase.schemaVersion 是 9。
  • 许可证交付未闭环：已有 GPL 分发文档，但根目录缺 LICENSE、THIRD_PARTY_NOTICES 和包内许可证目录，这在文档里也被列为 1.1 待办。
  • 枚举入库兼容性：Drift repository 用枚举 name 持久化，读取未知值直接抛错。后续改名或删除枚举会影响旧任务。
  • 自动化发布验证不足：当前项目没有看到类似 HandBrake 的 GitHub workflow；分析与测试要求在文档中，但没有 CI 强制执行。

值得学习

按迁移价值排序：先做低成本高收益，再考虑长期平台化。

向 CompressGo 学
  • 实际硬件编码探测：引入最小样本编码测试和缓存，而不只信任 -encoders 输出。
  • Windows 进程控制：参考其 windows-sys ToolHelp 暂停/恢复思路，为 Machining 的 Windows 队列补平台分支。
  • 事件化执行反馈：把命令、进度、完成、失败、取消结构化为统一事件或日志模型，后续 UI、CLI、测试都能复用。
  • 功能参数广度：time range、bit depth、AV1/VP9/ProRes/WebM、图片压缩都可以作为 1.1+ 的功能候选，但要沿用 Machining 的分层方式实现。
  • 批量参数快照：批量开始时缓存每个任务的生效配置，避免用户改右侧参数导致队列中任务语义漂移。
向 HandBrake 学
  • Job/Preset 协议：把压缩参数模板做成版本化 JSON，支持导入、清洗、迁移和默认预设。
  • 状态协议：扩展当前任务状态，记录 pass、pass_count、ETA、rate_cur、rate_avg、muxing/finishing 等结构化字段。
  • 扫描优先：先建立 source/title/stream 级扫描模型，再做高级音轨、字幕、章节、HDR、色彩、滤镜功能。
  • 依赖和补丁治理：为 FFmpeg 构建保留 hash、配置、补丁、源码获取方式和包内 NOTICE，而不是只保留构建脚本。
  • 跨平台 CI：将 analyze/test/build/runtime bundle check 纳入自动化，减少“本机可用、发布缺件”。
Machining 不应丢掉的优势

Machining 现在的领域分层和测试结构比 CompressGo 更清爽，这一点不该为了追功能而牺牲。最好的学习方式是：功能广度学 CompressGo，协议严密性学 HandBrake，但代码组织继续沿用 Machining 的 domain/application/infrastructure 分界。

迁移路线

建议按风险与收益分三批推进。

P0

先补协议和发布底线

  • 为 FFmpeg 主任务统一增加 -nostdin，明确是否使用 -y，并保留输出路径去重。
  • 修复 Windows 暂停/恢复：抽象 ProcessController，macOS/Linux 用 signal，Windows 用平台实现或降级为取消/重启提示。
  • 同步 schema 文档到版本 9，补枚举兼容策略。
  • 补根目录许可证和第三方 NOTICE，macOS Release 缺 FFmpeg 时改为失败或增加明确构建模式开关。
  • 加 CI：flutter analyze、flutter test、命令构造测试、打包 runtime 检查。
P1

增强媒体能力的可信度

  • 参考 CompressGo，实现硬件编码真实探测和缓存。
  • 把 FFmpeg 日志升级为结构化执行记录：命令、步骤、stderr 摘要、退出码、输出文件大小、耗时。
  • 把 CompressionAdvisor 的策略结果保存为任务执行快照，便于复现和排错。
  • 建立 preset JSON v1，先覆盖当前 smart/target size/CRF/codec/resolution。
P2

再扩功能面

  • 引入 time range、bit depth、更多容器/编码器、图片压缩，但每个能力都先加 command builder 测试。
  • 建立 HandBrake 式扫描模型：source → streams → chapters/audio/subtitle/crop/color 信息。
  • 抽象媒体处理 task type，为图片、视频、后续文件压缩共享队列和状态协议。
  • 建立发布检查清单：许可证、签名、公证、DMG、Windows runtime、另一台机器验证。
